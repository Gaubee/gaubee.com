# event-number-audit — 站点 event 编号与 slug 完整性体检

## 是什么

`src/content/events/` 用 `<5位序号>.<slug>.md` 命名，发布脚本扫目录自增序号。本工具核对三件事：

1. **编号重复**（硬错）：两个文件抢同一个序号；
2. **slug 重复**（硬错）：同一天同一份报告被发布两次；
3. **编号空洞**（提示）：删除重复后留下的空号，正常现象，不用补。

命名不合规的文件（不满足 `5位数字.xxx.md`）也会单独列出。

## 解决什么

2026-10-26 出过一次重复发布事故：一份 X 日报落了 3 个 event（01859/01860/01862），事后靠人眼发现并 `git rm` 两个。这个工具把「同一个 slug 出现两次」变成一条命令；编号空洞则作为背景信息保留，避免误判成故障。

## 怎么跑

```bash
bun tools/2026-11-11-event-number-audit/event-number-audit.ts
bun tools/2026-11-11-event-number-audit/event-number-audit.ts --root <仓库根>
bun tools/2026-11-11-event-number-audit/event-number-audit.ts --json
```

退出码：0 = 无重号/无重复 slug；1 = 有重复；2 = 目录缺失。纯本地只读。

## 真实示例输出（2026-11-11）

```text
event 1410 个｜编号 1~1900｜空洞 490｜重号 0｜重复 slug 0
  编号空洞（正常删除重复后的残留）：525, 526, 535, 536, 539, 545, 567, 595, 596, 611, 612, 614 …

EVENT AUDIT OK：无重号、无重复 slug
```

空洞 490 是历史删除/编号漂移的累计结果（早期归档重排、重复发布清理），不影响发布；真正危险的是重号与重复 slug，当前都是 0。

## 判读建议

- 发布前跑一次，或接到「同一天出现两个报告」的疑问时先跑它。
- 发现重复 slug 时只保留正式版，其余 `git rm`（保留 git 历史），不要回头补编号空洞。
