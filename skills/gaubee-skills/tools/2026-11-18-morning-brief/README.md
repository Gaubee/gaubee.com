# morning-brief — 06:00 跑批后的「一屏摘要」

## 是什么

06:00 的 launchd 任务跑完机械步骤后，06:30 的 agent 接手时要先判断「昨晚那轮跑成什么样」。
本工具把这件事折成一屏：跑批结果 → 各源变更 → 媒体与译文水位 → 待办清单。只读，不触发抓取。

## 解决什么

原来要 tail 几十行日志，再逐个 changes 文件对数字。2026-11-18 首跑，它一屏给出：

- 跑批 `ok 9 / skip 5 / fail 0`（含硬失败与软失败的分列）
- 星标新增 0 / 移除 0 / 元数据 6
- 依赖新技术首见 0 / 变更仓库 3
- X 11 条
- 提交 13 条（公开约 10 + 私有 3）
- 媒体 gen 39（9232 对象），staging 422 个文件
- X 日报已生成 / GitHub 日报已写 / 已发布 event 0 个（应为 2）

## 一个必须修掉的口径问题（首版踩过）

`last-run-fetch.json` 只保留**最后一次**运行。06:30 的幂等补齐一跑，就把 06:00 那轮
（20 项真抓取）覆盖成「9 ok / 5 skip」，摘要于是显示得像什么都没做。

修法：`daily-auto` 现在每次运行都往 `~/.gaubee-skills/automation/runs-<日期>.jsonl` 追加一行，
摘要优先读当日账本的**第一条**（真正的首轮），并注明当日共跑了几轮。

账本从 2026-11-18 起记。之前的日子没有 jsonl，摘要会退回读 `last-run-fetch.json`。

## 怎么跑

```bash
bun tools/2026-11-18-morning-brief/morning-brief.ts
bun tools/2026-11-18-morning-brief/morning-brief.ts --date 2026-11-17
```

退出码：0 = 摘要已出；2 = 数据缺失。默认报告日 = 昨天，抓取日 = 今天。

## 判读建议

- 「硬失败」必须先修：它意味着媒体没入卷或环境不合格，写日报会引用 404 的对象。
- 「软失败」逐条判断：比如 X 会话过期只影响 X 源，其它源照常出日报。
- 「已发布 event 0 个（应为 2）」是发布前的正常状态，不是错误。
