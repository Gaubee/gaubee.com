# stale-out-guard — 检查 /tmp 残留译文批次会不会覆盖已合并的译文

## 是什么

`x-translations-merge.ts` 会把 `/tmp/x-trans/out-*.json` 里的值写回翻译库。批次用完后没人清理，
下一次 finalize 又会合并一遍——中间若手工修过译文，就会被旧值静默覆盖。

本工具对比每个批次与当前翻译库，分成三种：值相同（安全）、键不存在（新增）、值不同（危险）。

## 解决什么

2026-11-22 实证：生成 X 日报时人话腔检测报「比喻(明喻) 2 / budget 1」，
根因是我把「图片模型」写成了「图**像**模型」——「像」被当成明喻。改完译文重跑 finalize，
报告里却还是旧文本：因为 `/tmp/x-trans/out-01.json` 还在，合并把它又写回去了。

修法有两层：`daily-auto` 在合并成功后把批次移进 `merged/`；本工具负责事前检查与事后取证。

## 怎么跑

```bash
bun tools/2026-11-22-stale-out-guard/stale-out-guard.ts
bun tools/2026-11-22-stale-out-guard/stale-out-guard.ts --archive
```

退出码：0 = 无冲突；1 = 有会被覆盖的键；2 = 路径异常。`--archive` 把冲突批次移到 `merged/`。

## 真实示例输出（2026-11-22）

实际运行时批次已被 daily-auto 归档，输出是：

```text
批次目录 /tmp/x-trans 里没有 out-*.json
```

用归档件构造一个冲突样本（把某条译文改成占位文本）后，检查器如实报出：

```text
批次文件 1 个：相同 13、新增 0、冲突 1
  ✗ out-01.json 2123898979695894874
      现译文：关于 minipg 这条路的一篇小文 https://progrium.xyz/
      批次值：旧版本译文（演示用）

建议：确认批次是旧的之后跑 --archive，或手工删掉这些 out 文件。
```

## 判读建议

- 「新增」不是问题：那是今天新导出的待翻译块，合并后会补进库。
- 冲突基本都是「批次比库旧」；确认后用 `--archive` 归档，别直接删（留着能追溯）。
- 它只看值是否相同，不判断哪个更好——哪个该留是人决定的。
