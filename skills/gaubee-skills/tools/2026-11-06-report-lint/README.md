# report-lint — 报告一致性门禁

## 是什么

两条绿色门：①**占位残留**——周/月/年/日报的「## 分析（agent 补充）」如果还留着生成器的 HTML 注释，说明分析没补就发出去了；②**星标累计数对账**——日报里「总数 M」必须等于该日按 `starred_at` 精确统计的累计数。

关键语义：占位只对**已发布**的报告考（未发布的骨架是草稿，不算问题）；数值只对写了星标数的日报考。

## 解决什么

两条都是真实事故：

- 2026-11-04 补跑时，四条日报的「总数」靠心算，三条各少一位（1730/1738/1739 应为 1731/1739/1740），靠人工重算才发现回改。
- 周报/月报骨架的占位注释会被生成器原样带出，补分析这一步漏掉就会把占位发到线上。

## 怎么跑

```bash
bun tools/2026-11-06-report-lint/report-lint.ts                 # 默认 since 2026-10-01
bun tools/2026-11-06-report-lint/report-lint.ts --all           # 全历史
```

退出码：0 全绿；1 有占位残留或数值不一致；2 环境异常。

## 真实示例输出（2026-11-06 首跑）

首跑抓到 4 项，其中 1 项是**已发布**的真错误：

```text
报告一致性问题 4 项（since 全部）：
  - weekly/2026-W40.md：分析节仍是占位注释       ← 未发布草稿，改进后不再报
  - yearly/2025.md：分析节仍是占位注释            ← 同上
  - yearly/2026.md：分析节仍是占位注释            ← 同上
  - daily/2026-10-28.md：写「总数 1722」，实测该日累计 1725   ← 真错误
```

处理：前三条按「只考已发布」的新语义自动豁免（它们从未发布成事件）；第四条同时修正了报告源与已发布事件 01869 的数值（只改数字，报告日期不动），复跑即全绿：

```text
report-lint OK：占位与分析齐全、星标累计数一致（since 全部）
```

## 建议用法

放在发布之前跑：`report-lint` 绿了再 `publish.ts`，比发布后再发现数字错成本低得多。
