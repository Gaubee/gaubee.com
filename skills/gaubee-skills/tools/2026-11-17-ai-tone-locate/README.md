# ai-tone-locate — 把 ai-tone 的「密度超标」落到具体句子

## 是什么

`ai-tone-metrics` 按文件算**密度**，报「顿号罗列≥3 5.69/0.7k RED」，但不告诉你哪几句贡献了这些顿号。
本工具用同一批正则逐句扫描，列出命中的原文和行号，把「肉眼找句子」变成照单修改。

只做定位，不做判定。红线仍以 `ai-tone-metrics` 的退出码为准。

## 解决什么

2026-11-16 的日报被报 `顿号罗列≥3 5.69/0.7k RED`，实际有 4 处并列结构散在星标改名说明、
spool 性能账、chmod 说明、管道汇总四段里，得逐段找到才能改。这类工作纯机械，
本工具首跑就把它变成 4 行待改清单。

## 两个必须避开的误判（首版都踩过）

1. **过滤掉列表项 = 什么都扫不到**。第一版把 `- ` 开头的行当作 frontmatter 排掉，
   结果 11-15 报告「19 句扫描」里有效句子为 0。正文的提交段全是列表项，不能整体排除。
2. **把星标条目算进顿号**。`- [owner/name](url) — 说明` 里的顿号属于条目描述，
   `ai-tone-metrics` 的预算主要针对行文，算进来会虚高——11-15 报告本身已达标，
   首版却报了 2 句。修正后只扫正文，同一文件回到 0 命中。

## 怎么跑

```bash
bun tools/2026-11-17-ai-tone-locate/ai-tone-locate.ts reports/daily/2026-11-16.md
bun tools/2026-11-17-ai-tone-locate/ai-tone-locate.ts reports/daily/2026-11-16.md --only 顿号罗列≥3
```

退出码：0 = 有命中并已列出；1 = 无命中（可能超标全由小词累积）；2 = 用法/文件错误。只读。

## 真实示例输出（2026-11-17，扫 2026-11-09 报告）

```text
2026-11-09.md：逐句定位（31 句扫描）

【顿号罗列≥3】4 句命中 —— 三个以上顿号并列。改成短句、或只留两个、或用分号分层
  L25  ×1  **Stoa 改名与已读同步（jixoai/stoa，15 条）**：fde2e-workers 正式改名 Stoa（包、CLI、env 双读，远端仓同步更名）；
  L27  ×1  **汇报通道插件化（jixoai/fde2e，23 条）**：report-channel 做成 ZCode 插件，侧栏面板、项目级自动启用、UserPromptSubmit …
  L27  ×1  子模块指针批量推进，带上 browser 0.2.18、omni 0.4.15/0.4.16、cu 0.4.1 GA。
  L28  ×1  **浏览器分屏与标签组（jixoai/fde2e-browser，5 条）**：0.2.18 补上分屏（Edge 标准双 pane 加可拖动分隔条）、Chrome 语义完整的标…

共 4 句需要改。改完重跑 ai-tone-metrics 确认 RED 清零。
```

同一天扫已达标的 2026-11-15 报告是 0 命中，说明过滤器没有过度报警。

## 判读建议

- 命中数 > 0 时逐个改；改完**必须**重跑 `ai-tone-metrics`，因为密度是全文件统计，改一处可能还差一点。
- 命中数 = 0 但 metrics 仍报 RED：说明超标来自大量重复小词而非可切分的结构，这时按 metrics 原表逐项看。
- 它的正则与 metrics 同源但**阈值不复制**——避免两处阈值漂移导致「工具说没问题但门禁不过」。
