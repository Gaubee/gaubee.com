# staging-clean-preview — 周清理前的「按条目归组」核对视图

## 是什么

`staging-clean` 的 dry-run 是平铺清单，2026-11-16 那次有 446 个文件一条条列出来，人没法逐条核对。
本工具把清单折成「按推文 id 归组」的视图，每组给出文件数、总大小、最老 mtime、入卷比例，外加三项自检：

1. **入卷**：每个文件的 canonical key 是否在 manifest 里；
2. **孤儿**：该 id 是否还在 x.json 快照里；
3. **HLS 完整**：有 `.m3u8` 就必须有 `.ts` 段（只有播放列表 = 残缺条目）。

核对量从 446 行降到几十行。

## 解决什么

周清理的四安全条件（已入 manifest / 卷已发布 / mtime>7 天 / 在 staging/x 下）由 `staging-clean` 自己判，
本工具补的是**人工核对这一关的可读性**：同一个视频的 `.m3u8` 加 20 个分片散落在平铺清单里，
看不出它们属于同一条、也看不出是否完整。归组之后，一眼能看出「这条 21 个文件都在卷里」。

## 一个必须按完整 key 比对的坑

第一版用「文件名后缀」判断是否入卷，结果 45 个条目全部误报 `未入卷`——有两个原因：

- manifest 里的 key 是 `x/2026-11/2120...-1.jpg`，**不带 `cdn-media/` 前缀**；
- 不同月份目录会有同名文件（`-1.jpg` 极常见），只比文件名会跨月冒充。

修正后按「staging 相对路径」与 manifest key 精确相等比对，45 个条目全部通过。

## 怎么跑

```bash
bun tools/2026-11-16-staging-clean-preview/staging-clean-preview.ts                # 默认 7 天
bun tools/2026-11-16-staging-clean-preview/staging-clean-preview.ts --older-than 1
bun tools/2026-11-16-staging-clean-preview/staging-clean-preview.ts --json
```

退出码：0 = 全部组通过自检；1 = 有组不完整/未入卷/孤儿（**先别执行 --execute**）；2 = 路径异常。只读。

## 真实示例输出（2026-11-16，阈值 1 天以便看到样本）

```text
staging 待清理预览：manifest gen 37，45 个条目 / 250 个文件 / 173.8 MB（仅计 mtime 超 1 天的）
  ✓ 2119618553565639016  1 文件 0.1MB  最老 2026-11-10  入卷 1/1
  ✓ 2119684071299436891  21 文件 12.9MB  最老 2026-11-10  入卷 21/21
  ✓ 2119750298495558113  12 文件 1.9MB  最老 2026-11-10  入卷 12/12
  …另 20 个条目
```

同一天用默认 7 天阈值跑是 0 个条目——因为当天已经执行过清理，超期的都删了（符合预期）。

## 判读建议

- 它的定位是**人工核对辅助**，不替代 `staging-clean` 的四条件判定，也不自己删文件。
- 出现 `✗` 就先别 `--execute`：要么是那次打包漏了，要么是 HLS 分片没写完。
- 默认 7 天与清理保留期一致；用 `--older-than 1` 可以提前看「再过几天会删什么」。
