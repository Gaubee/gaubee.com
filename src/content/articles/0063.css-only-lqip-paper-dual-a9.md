## 摘要

**研究问题。** Lean Rada 的 CSS-only LQIP 用一个 Oklab 基色和六个中性灰 `hard-light` 径向层，在 20 bit 内构造低清占位图。它的光感非常稳定，但一个基色不能同时表达空间上分离的色相，例如上方蓝天与下方红土。本文讨论的不是重写这套光场，而是在不改变其几何、层序、stop 与混合模式的前提下，如何把 32 bit 的其余容量交给底色场。

**方法。** 研究首先将原作者编码器固定到提交 `7b6739c`，并采用原文章中为防站点样式演进而保留的六层 CSS。随后定义 `#RRGGBBAA` 载荷：12 bit 保留六格 Paper 光场，18 bit 分别用于高精度单色 `L6+a6+b6` 或两个 `L3+a3+b3` 的 Dual-A9 endpoint；`--lqipm` 的四个 mode 表示方案和编码坐标。收敛实验对 34 个本地 artifact 构造 native 与居中反向裁切，以三档 Gaussian 模糊目标的 Oklab RMSE 排列候选，并用真实 Chrome 检查离线渲染器与公开 demo 是否互锁。

**结果。** 在该私有样本和该度量下，Dual-A9 的方向胜者在 34 个 artifact 中有 33 个低于相应的单色胜者；平均 Oklab RMSE 分别为 `0.08405` 与 `0.10263`。136 个候选的 Chrome/数学像素互锁平均 RMSE 为 `0.00509`，最大为 `0.00651`。前一组数字描述内部比较，后一组数字描述解码器近似程度；两者都不是人类偏好结论。

**结论。** PaperCSS 的关键价值不是六个小格，而是以固定的中性 `hard-light` 光场把低频明暗从色相表示中剥离。保留该光场、扩展底色场，能解决一部分空间色彩不足；一维 A/B 渐变仍无力表达局部多色结构。协议正确性、自动误差和人工视觉判断必须作为三条独立证据链维护。

**关键词：** CSS-only LQIP；Oklab；低频图像近似；PaperCSS；浏览器互锁；可复现实验

## 2. 原始 CSS-only LQIP：20 bit 如何形成一张“有光”的图

原方案的出发点很克制：占位图不需要保留对象边缘，也不可能存下真实缩略图；它只需要在原图加载前给人一个与原图同向的低频印象。于是作者没有把 20 bit 平均切成六块颜色，也没有去编码六个缩略像素，而是拆成两种不同职责：一个色相底子，六个相对明暗控制量。

```text
20-bit payload
┌──────┬──────┬──────┬──────┬──────┬──────┬────┬─────┬─────┐
│  ca  │  cb  │  cc  │  cd  │  ce  │  cf  │ ll │ aaa │ bbb │
├──────┼──────┼──────┼──────┼──────┼──────┼────┼─────┼─────┤
│ 2bit │ 2bit │ 2bit │ 2bit │ 2bit │ 2bit │2bit│ 3bit│ 3bit│
└──────┴──────┴──────┴──────┴──────┴──────┴────┴─────┴─────┘
  六个相对亮度槽（12 bit）              一个 Oklab 基色（8 bit）
```

它输出为有符号整数 `packed - 2^19`，合法范围是 `[-524288, 524287]`。这个整数的表示方式不是视觉算法本身，重要的是每一段数据所承担的角色。

### 2.1 编码端：一个基色与一个 3 x 2 明暗观察

固定提交的编码器有两条并行管线。

```text
输入图像
   │
   ├─ 每 10 个 RGB 像素采样一次
   │     -> Color Thief / MMCQ，生成 4 色调色板
   │     -> palette[0] 作为基色
   │     -> sRGB 转 Oklab，穷举 256 个 L2+a3+b3 码字
   │
   └─ Sharp resize(3, 2, fit: fill)
         -> sharpen(sigma: 1)
         -> raw RGB 六像素
         -> 每个像素的 Oklab L 相对于基色明度量化为 ca..cf
```

这几个细节决定了“复现”是否真的是复现。

首先，基色不是原图平均色，也不是按 Oklab `a/b` 自己分桶得到的最大族。编码器从每十个 RGB 像素抽样，调用 Color Thief 的 MMCQ 生成四个颜色，再取 `palette[0]`。基色经 sRGB 到 Oklab 的转换后，不是三个分量各自取整，而是枚举全部 `4 x 8 x 8 = 256` 个码字，使用作者定义的色度重标定距离选择最近者。

对应的解码码本是：

```text
L(ll)  = ll / 3 * 0.6 + 0.2
a(aaa) = aaa / 8 * 0.7 - 0.35
b(bbb) = (bbb + 1) / 8 * 0.7 - 0.35
```

其次，`ca..cf` 不是把原图裁成六个矩形之后取平均亮度。作者调用 Sharp 的 `resize(3,2,{fit:"fill"})`，随后 `sharpen({sigma:1})`，再读取六个 raw RGB 像素。第 `i` 个像素的 Oklab 明度 `Li` 被编码为：

```text
vi = clamp(0.5 + Li - Lbase, 0, 1)
qi = Math.round(vi * 3)      // qi ∈ {0,1,2,3}
```

这里保存的是“相对基色亮度”而不是绝对灰度。若把它改成原图局部平均、去掉锐化，或在 Python 中用 ties-to-even 的 `round` 替代 JavaScript `Math.round`，得到的 12 个高位就可能不同。早期实验恰好犯过这些错误，相关分数已经作废，不能继续作为原论文的成绩。

### 2.2 解码端：不是六个色块，而是六个中性光场

浏览器先从 `ll/aaa/bbb` 恢复一个平坦的 Oklab 底色。其上再放六个同为中性灰、不同强度的径向渐变。`ca`、`cb`、`cc` 位于上排 `x = 16.67%, 50%, 83.33%`、`y = 25%`；`cd`、`ce`、`cf` 位于下排同样的三个 `x` 与 `y = 75%`。每个径向光斑的半径是 `50% x 75%`。

```text
               x: 16.67%        50%        83.33%
            ┌───────────┬───────────┬───────────┐
y = 25%     │    ca     │    cb     │    cc     │
            ├───────────┼───────────┼───────────┤
y = 75%     │    cd     │    ce     │    cf     │
            └───────────┴───────────┴───────────┘

q = 0 / 1 / 2 / 3  ->  neutral grey = 20% / 40% / 60% / 80%
```

径向层不是突然从实色跳到透明。文章 CSS 用一组分段线性 stop 近似二次衰减：半径位置 `0/10/20/30/40/60/70/80/90/100%` 的 alpha 为 `1/.98/.92/.82/.68/.32/.18/.08/.02/0`。因此，相邻单元会很大范围地重叠，画面不会退化为六个硬边矩形。

CSS 声明的背景顺序从上到下是 `ca, cb, cc, cd, ce, cf, flat base`；实际合成应从底向顶理解：

```text
flat Oklab base -> cf -> ce -> cd -> cc -> cb -> ca
```

六层都使用 `hard-light`。这件事非常容易被误读成“在底色上加六个白色高光”，但 `hard-light` 不是单向提亮：用较亮的中性灰会提高底色通道，用较暗的中性灰会压低它。它们不改变中性灰本身的色相，却会在每个位置上调制底色的明暗和对比。

### 2.3 为什么 20 bit 看起来比六个色块更像照片

原方案实际上把图像近似拆成两个低频问题。

```text
图像低频外观
   = 近似统一的色相基底
   + 平滑、重叠、相对亮度调制
```

这个拆法的工程价值很高。六个亮度槽只花 12 bit，却提供一个跨越整张元素的连续场；中性 `hard-light` 既能使暗处继续沉下去，也能让亮处抬起来。人并不会把它读成六个“像素”，而会读成一张有起伏、有曝光方向的表面。固定几何、固定 stop 和固定层序是这种欺骗能够稳定成立的原因，不是可以随意调参的装饰。

它的限制同样明确：基色只有一个 Oklab 色相。六格存的也是相对亮度，不是局部色相。蓝天压着红地、海水贴着橙色沙滩时，Paper 光场可以重建“上亮下暗”或“左暗右亮”，却不可能同时把蓝和红放进同一个平坦底色。这是容量边界，不是多加一条色差惩罚就能修好的采样 bug。

## 3. 从复现基准到研究决策：什么该冻结，什么可以扩展

最初的错误不是从 PaperCSS 出发，而是把“论文效果”当成一个大致相像的画面。旧 Python 编码器以自定义 `(a,b)` 最大族替换 MMCQ，以直接量化替换 256 码字穷举，又漏掉 Sharp `resize(3,2)+sharpen(sigma=1)`。其渲染模拟还曾反转渐变边缘 alpha 和 `hard-light` 合成层序。输出的图也许能看，但它没有资格报告原论文效果；旧的“论文 RMSE”因此全部失效。

基准修正之后，问题反而变得更简单。Paper 光场已经是用户视觉上认可的部分，继续把六层改成 8 层、12 层，或重新设计新的光源拓扑，都会把“颜色不足”的问题和“光感变了”的问题搅在一起。因此当前研究把这个边界冻结：六个光斑的几何、灰阶、stop、层序、混合模式都不动；只研究最下面那一层可以承载什么。

研究过程中曾保留 Axis-16、二维 Mesh-2、五基色、A8/A9 与旧多布局分支。这些文件在 `experiments/convergence/archive/`，它们不是被遗忘的半成品，而是反例证据：增加位数、给渐变加角度，甚至增加 endpoint，并不自动改善视觉结果。一旦它们改变了固定 Paper 光场，或者没有通过同等级浏览器互锁与人工判断，就不应进入公共 mode。

最终收敛成两个事实：

```text
必须保留：六个中性 hard-light Paper light 的视觉角色
必须扩展：底色的空间色相表达
不应伪装：自动评分可以替代视觉选择
```

## 4. 32-bit 四模式协议

协议向页面只暴露两个属性：

```css
--lqip: #RRGGBBAA;
--lqipm: 0 | 1 | 2 | 3;
```

采用 CSS `<color>` 而不是再编码一个有符号 32-bit 整数，是一个实现正确性决定。Chromium 对 `calc(var(--lqip) + pow(2,31))` 一类大数计算会以浮点表示，低位字段可能发生舍入偏移；从 `rgb(from var(--lqip) ...)` 中解出四个 8-bit 通道则保持在可靠范围。

### 4.1 字节布局

`R` 放入前四个 Paper 亮度槽，`G` 放入后两个槽、mode 和颜色区的高位；`B/A` 放入其余颜色位。

```text
                 bit 7                                   bit 0
R        ┌──────────┬──────────┬──────────┬──────────┐
         │    ca    │    cb    │    cc    │    cd    │
         └──────────┴──────────┴──────────┴──────────┘
G        ┌──────────┬──────────┬──────────┬──────────┐
         │    ce    │    cf    │     m    │     h    │
         └──────────┴──────────┴──────────┴──────────┘
B        ┌──────────────────────────────────────────────┐
         │           scheme-specific bits 15..8          │
         └──────────────────────────────────────────────┘
A        ┌──────────────────────────────────────────────┐
         │           scheme-specific bits 7..0           │
         └──────────────────────────────────────────────┘
            2 bit      2 bit      2 bit       2 bit
```

前 12 bit 永远是 `ca..cf`。其余 18 bit 解释取决于 `m`：

| mode | payload 内 `m` | 底色场 | 18-bit 颜色解释 | 编码坐标 | 显示坐标 |
| ---: | --- | --- | --- | --- | --- |
| 0 | `00` | Paper single | `L6+a6+b6` | 原图 | 原图 |
| 1 | `01` | Paper single | `L6+a6+b6` | 源图顺时针 `+90deg` | 映射回原图 |
| 2 | `10` | Dual-A9 | `A(L3+a3+b3) + B(L3+a3+b3)` | 原图 | 原图 |
| 3 | `11` | Dual-A9 | `A(L3+a3+b3) + B(L3+a3+b3)` | 源图顺时针 `+90deg` | 映射回原图 |

对于单色，`h` 是 18-bit `L6+a6+b6` 码的最高两位；对于双色，`h` 分别放 A/B 两个 9-bit 码的最高位，`B/A` 通道保存二者各自低八位。`--lqipm` 与 payload 内的 `m` 必须一致。前者让 CSS 选中分支，后者让字节有自描述性；CSS 不能可靠地断言二者相等，这条不变量由编码器、golden 和发布回归共同维护。

### 4.2 两个 Oklab 码本，以及为什么是 A9

两种模式落在同一个受限 Oklab 盒子：

```text
L = qL / (2^l - 1) * 0.6 + 0.2
a = qa / 2^a * 0.7 - 0.35
b = (qb + 1) / 2^b * 0.7 - 0.35
```

单色模式使用 `(l,a,b) = (6,6,6)`，一共 18 bit。Dual-A9 用两个对称的 `(3,3,3)` endpoint，各为 9 bit。它不是“把每个颜色做得更亮”，也不是试图让两端永远拉开距离。Paper 的 12 bit 光场继续承担低频明暗；18 bit 的任务是回答另一个问题：底色究竟只有一个色相，还是可以沿一条连续轴从 A 变到 B。

CSS 端使用：

```css
linear-gradient(var(--paper-base-angle) in oklab,
  var(--paper-base-start), var(--paper-base-end))
```

这不是装饰性选择。若在 sRGB 中线性插值，某些蓝色到暖色的路径会经过更宽的紫红区，曾经放大输出中的酒红偏移。颜色场在 Oklab 中插值，之后才接受固定六层 `hard-light` 调制。

### 4.3 旋转 mode 是坐标合同，不是第二套算法

模式最低位只表示编码坐标。奇数 mode 先将源图顺时针旋转 90 度，运行完全相同的编码器，然后由 CSS 把底色方向、径向光斑中心和椭圆半径映回原始显示坐标。

```text
原图
  │ rotate +90deg
  ▼
同一套 single / Dual-A9 编码器
  │ payload: mode 1 或 3
  ▼
CSS inverse coordinate mapping
  │
  └─> 原始画布上的颜色场 + 六个 Paper light
```

因此 mode 2 与 3 没有“vertical 算法”和“horizontal 算法”的区别，mode 0 与 1 也没有。差异只是输入坐标和反向显示坐标。若让 mode 3 使用不同的颜色采样逻辑，或只旋转完整元素而不映射最后一层线性渐变与六灯几何，就会产生同一张原图在 0 度与 90 度之间无端变色的问题。

## 5. 颜色提取：从“取两块平均色”到前向渲染裁决

双色最诱人的错误实现，是上半部取 A、下半部取 B，再做线性渐变。这会将 Paper 光场已经负责的亮度再写进端点：黑色阴影把一端拉脏，白色高光把端点拉灰；同一张图旋转后，端点甚至会变成另一种颜色。它恰好违背了第 2 节中原方案的职责分离。

当前搜索不把任何中间步骤当成最终颜色。它从中间调色度、观察到的色场和去光反解色场生成候选，但这些都只是候选池；最终必须将量化后的码字放回七层渲染器，由完整输出决定。

```text
非预乘 sRGB RGBA
   │
   ├─ 全部像素：亮度与 3x2 Paper light 拟合
   ├─ 中间调权重：仅为 a/b 色相提出候选
   │     └─ 黑白极值不主导色相，但不从亮度拟合删除
   ├─ CSS gamut-mapped Oklab 码本：量化 A/B 或 single
   └─ seven-layer forward render
          -> 与低频目标比较
          -> 选择候选
```

为什么要强调 gamut mapping？反解色可能落在 CSS/sRGB 可表示范围外。若把一个被 clamp 的反解色直接当作真实端点，光场造成的偏色会被二次写进底色；若反过来在候选阶段直接淘汰所有越界色，也会把本来可经前向渲染获得较好结果的颜色错误剪掉。当前做法是用 CSS 实际可见的量化色建立候选集，再让最终的七层输出裁决。

这仍不是一个“色彩分离问题已经解决”的声明。`pexels-thteam-11311209` 的局部黄灯、肤色与黑色需要在很短距离内共存，固定六灯加一条 A/B 轴仍可能把黑端推向酒红。那是当前模型表达力不够，不应用强制 endpoint 色距、额外色向量惩罚或“旋转至少改善 5%”这类规则掩盖。

## 6. 实验设计与测量

实验页故意把自动选择拆成三个独立页面，而不是在一张大表里混排四种候选：

```text
single-modes.html   mode 0  vs mode 1
dual-modes.html     mode 2  vs mode 3
winners.html        上述两场自动胜者再比较
```

当前 `paper-modes-artifacts.json` 有 34 个 artifact：17 个 portrait、17 个 landscape。每一张参考图贡献 native 样本和居中反向裁切样本，从而让横向与纵向结构都出现在两类构图里，而不是把“图片宽高”误写成“应选的方向”。每个 artifact 固定生成 `single-0`、`single-1`、`dual-2`、`dual-3` 四个候选。

```text
reference
   ├─ native
   └─ centred reciprocal crop
          │
          ├─ source coordinates: 0deg
          └─ source coordinates: +90deg
                 │
                 └─ Paper single / Dual-A9 candidates
                        │
                        └─ original display coordinates
                               -> Gaussian σ 20, 32, 48 targets
                               -> mean Oklab RMSE
```

自动度量是三档 Gaussian target 的平均 Oklab RMSE。它不是“原图逐像素相似度”，因为 LQIP 本来只表达低频；也不附加任意百分比门槛、强制色距或方向偏好。每个对比页会为较低数值画绿色 outline，但这个框只说明该测量下的排序。人看到颜色丢失而机器只看到局部光影改善时，绿色框不拥有裁决权。

## 7. 结果与解释

表 1 直接汇总当前 artifact。数值没有人工重选，也不对私有样本集作显著性推断。

| 度量 | 结果 |
| --- | ---: |
| artifact 数 | 34 |
| portrait / landscape | 17 / 17 |
| single 方向胜者：mode 0 / mode 1 | 15 / 19 |
| Dual-A9 方向胜者：mode 2 / mode 3 | 20 / 14 |
| 最终胜者：mode 2 / mode 3 / single-1 | 20 / 13 / 1 |
| Dual-A9 胜者严格低于单色胜者 | 33 / 34 |
| single 胜者平均 Oklab RMSE | 0.10263 |
| Dual-A9 胜者平均 Oklab RMSE | 0.08405 |
| 最终胜者平均 Oklab RMSE | 0.08368 |

这组结果支持一个很窄的观察：在这 34 个 artifact、这三档 Gaussian 模糊和这个前向评分下，允许底色沿一条 A/B 轴变化，通常比高精度单色得到更低的 Oklab 误差。它不支持“Dual-A9 对所有图片都更好”的结论。局部多色、强主体、窄范围的黑黄肤色结构仍会让一维色场与 Paper 光感发生取舍；图像加载前的短暂感知也不是一个只由 RMSE 决定的问题。

这也是为什么目前不把 Archive 中的 Axis-16、Mesh-2 或五基色直接提升为新的正式 mode。它们可能增加容量，却同时增加新的坐标约定、CSS 分支和光场假设。要进入协议，必须重新走完原论文基准核对、载荷定义、浏览器互锁和人工视觉验收，而不是只在一张排行榜上排名更高。

## 8. 从模型到公开页面：四层互锁

“协议可打包”与“浏览器画面正确”是不同问题；“浏览器画面正确”与“人觉得更还原”又是第三个问题。当前工程将三者拆开，再各自保留证据。

| 层 | 事实源 | 能够证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| CSS 解码 | `frontend/lqip.css` | `#RRGGBBAA` 与 `--lqipm` 如何构成七层背景 | 哪个候选更接近人的观感 |
| 协议实现 | Go、Rust、Zig、TypeScript | pack/decode 字段、空输入和公开 API 通过同一批 golden | 四门语言使用同一套收敛搜索 |
| 收敛实验 | `experiments/convergence/` 的 TypeScript | 本文 34 个 artifact 及表 1 的生成过程 | 对未见图片的统计结论 |
| Chrome 与发布回归 | 浏览器脚本、公开静态 demo | 数学预览、CSS 与 iframe 没有悄悄分叉 | 人类对光感的最终判断 |

`paper-mode-browser-verify.sh.ts` 把 34 x 4 个候选放入真实 Chrome 的 `frontend/lqip.css`，并与对应数学预览逐像素比较。最近一次可重复检查如下：

| 检查项 | 结果 |
| --- | ---: |
| Chrome candidate 数 | 136 |
| 平均像素 RMSE | 0.00508658 |
| 最大像素 RMSE | 0.00651314 |
| 最大偏差单元 | Fahrul Azmi native / mode 0 |

这个检查只回答“离线数学渲染器是否足够接近当前 Chrome CSS”。它不是 LQIP 对原图的误差，更不是感知质量分数。解码器还显式固定 `background-color: #111619` 和 `background-size: 100% 100%`，避免 `hard-light` 的透明尾部依赖 iframe 宿主的底色或默认背景尺寸。

公开 demo 曾经暴露过一个很具体的失败模式：四个 mode 格子混用了不同 fixture 的 payload，导致文章内的单色效果不可能与实验页同名 artifact 相同。现在四格统一绑定到 `reference-fahrul-azmi-Q1l1ofdVYl4-unsplash-native`，发布数据如下：

## 9. 有效性威胁与当前边界

1. **样本不是总体。** 34 个 artifact 经人为选择并加入 reciprocal crop，不是随机抽样，也不公开分发。表 1 只能支持本次内部比较。
2. **指标不是视觉。** Oklab RMSE 在低频模糊目标上能稳定排列一些候选，却会漏掉人对主体、色相丢失和摄影光感的判断。绿色框只是定位人工复核点。
3. **浏览器不是抽象 CSS。** 当前互锁在给定 Chrome、给定尺寸下成立。相对颜色函数、`pow()`、`mod()`、`round()` 与 Oklab 插值的跨浏览器表现需要独立验证。
4. **Dual-A9 不是二维色场。** 单条 A/B 轴只能表达一维、连续的色彩变化。它无法精确复原三处及以上彼此独立的局部色相，也不能把固定 Paper light 当成真正的局部颜色层。
5. **协议不是搜索算法。** 四语言实现锁定的是公共 payload 语义；收敛实验的 TypeScript 搜索是研究实现。两者不能因同属一个仓库而被写成“所有语言已复现同一优化器”。

## 10. 可获得性与复现

解码事实源是 [`frontend/lqip.css`](https://github.com/Gaubee/lqip-blurhash/blob/main/frontend/lqip.css)。四语言 pack/decode 与 golden 位于仓库根目录的 `go/`、`rust/`、`zig/`、`typescript/`；原始基准核对、收敛程序和生成页面位于 `experiments/convergence/`。本地参考图不随仓库公开；缺失它们时，不能声称复现表 1，但仍可独立运行过程化 golden 与源码级检查。

```sh
(cd go && go test ./...)
(cd rust && cargo test)
(cd zig && zig build test)
(cd typescript && pnpm test)

cd experiments/convergence
bun run prototypes/paper-modes/build.sh.ts
bun run prototypes/paper-modes/build-pages.sh.ts
bun run prototypes/paper-modes/election-regression.sh.ts
bun run paper-mode-browser-verify.sh.ts
bun run prototypes/paper-modes/article-demo-regression.sh.ts
bun run prototypes/paper-modes/article-demo-browser-verify.sh.ts
```

人类验收入口是 `experiments/convergence/prototypes/paper-modes/out/index.html`，不是没有 winner 标记的像素互锁 fixture。发布文章时，还必须在 Gaubee 构建后重复两条 article demo 回归，避免 iframe 回退到不同 payload 或不同 CSS。

## 11. 结论

Lean Rada 的 20-bit 方案给出了一个比“六格低清图”更有用的模型：用一个基色承担色相，用六个重叠的中性 `hard-light` 场承担低频明暗。这也解释了它的优越性和它的硬边界。六个 light 槽能塑造光，却不会凭空产生空间色相。

当前 32-bit 协议不重写那套已被视觉认可的光场。mode 0/1 将额外容量交给更密的单色 Oklab 码本，mode 2/3 将它交给一条 Dual-A9 色场；奇数 mode 只改变编码与显示坐标，不分叉颜色算法。在有限的内部实验中，Dual-A9 通常取得更低的低频色差，但一维底色仍无法表达局部多色图像。

这份研究的交付不是一个“最终最佳算法”的宣言，而是一组可追溯的边界：原论文基准被冻结，位布局和坐标合同明确，代码与浏览器输出可以互锁，自动分数只用于排序，人仍然保有最后的视觉选择权。后续若引入新的色场，必须以相同的证据标准重新开始，而不能用复杂评分函数把未解决的问题写成已解决。
