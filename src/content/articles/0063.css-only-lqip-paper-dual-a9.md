[Lean Rada 的 CSS-only LQIP](https://leanrada.com/notes/css-only-lqip/) 最打动我的地方不是它把图片压成了一个小数字，而是那六个光斑。它们让一个平面颜色看起来像一张已经被拍摄过、压缩过的照片。这个光感很难复制，甚至很难解释：颜色只是底，真正让大脑相信“这是一张图”的是明暗结构。

问题也从这里开始。单色底只能表达一个主要色相。天空和地面、灯光和皮肤、蓝色的上半部和红色的下半部，都会被迫挤在同一个颜色里。我的第一反应是增加颜色、增加布局、增加方向。实验很快证明，容量不是唯一矛盾：只要把 Paper 光场改坏，新增的颜色就不值得了。

## 先把基准找回来

在这项工作里，最大的风险不是某个矩阵写错，而是我们很容易把自己的评分器当成真理。早期版本用自定义的网格误差挑选布局，数字越来越漂亮，浏览器里的占位图却不像原论文。后来我把原论文的 CSS 和编码步骤单独保存成 `frontend/lqip-paper-reference.css`，把它当作不可修改的基准。

基准的工作方式可以缩成一张图：

```text
一张基色
   + 六个中性灰 hard-light 光斑
   = PaperCSS 的光感
```

所以颜色修复应该发生在底色场，而不是重写光斑。我们最终保留了六层 radial gradient 的 stop、层序、source-over 合成和几何，只改变第七层底色：单色模式使用纯 Oklab 颜色，双色模式使用 Oklab 的 A→B 线性渐变。

## 四个 mode，而不是四套算法

当前公共协议只有两个 CSS 自定义属性：

```css
--lqip: #RRGGBBAA;
--lqipm: 0 | 1 | 2 | 3;
```

`--lqip` 的四个通道仍然是 32 bit，只是它们不再被当成一个需要加偏移的有符号整数：

```text
R = ca cb cc cd       4 × 2-bit Paper light cells
G = ce cf mode colour 2 × 2-bit light + 2-bit mode + colour high bits
B/A = mode-specific colour bits
```

模式的分配是成对的：

| mode | 底色                           | 编码坐标           |
| ---: | ------------------------------ | ------------------ |
|    0 | 一个 `L6+a6+b6` Oklab 颜色     | 原图               |
|    1 | 一个 `L6+a6+b6` Oklab 颜色     | 源图顺时针旋转 90° |
|    2 | 两个 `L3+a3+b3` Oklab endpoint | 原图               |
|    3 | 两个 `L3+a3+b3` Oklab endpoint | 源图顺时针旋转 90° |

因此：

```text
rotation = mode mod 2
scheme   = floor(mode / 2)
```

模式 3 不是“另一个 Dual-A9 算法”。编码器把源图旋转后，仍然执行同一个 vertical 3×2 搜索；CSS 负责把颜色场和光斑坐标映射回原画布。这个区别很重要。它把“方向选择”从算法实现里拿出来，变成协议中一个可扩展的枚举位。

## 颜色不能从两个像素里取

双色方案最容易写成一个看似合理、实际很脆弱的算法：取图像上半部和下半部的平均色，再把它们量化。这样做会把 Paper 光场已经完成的明暗工作再次吸收到颜色里。黑色区域会把端点拉暗，白色高光会把色相拉灰；同一张图片旋转后，颜色甚至会换一套。

现在的编码流程让颜色候选接受完整的 forward render：

```text
RGBA（非预乘 sRGB）
      │
      ├─ Oklab 与中间调色度权重
      ├─ 穷举 3×2 Paper light cells
      ├─ 生成观察色场、去光反解色场和中间调色簇候选
      ├─ 映射到实际 CSS gamut 后量化
      ├─ 重新渲染六层光场 + 底色场
      └─ 用渲染结果裁决候选
```

黑白极值可以退出 `a/b` 色相投票，因为它们更像光场证据；但它们不能从亮度和光场搜索里删除。反解越界也只能降低候选的色相可信度，不能把被 clamp 后的颜色当作新的事实。

目标不是让两个 endpoint 尽量分开。人为强制色距，或者规定“90° 至少改善 5% 才能获胜”，只是在替评分器做决定。实际实现用 sigma 20、32、48 三个 Gaussian target 的平均 Oklab RMSE 作为可解释的自动排序；颜色和光感冲突时，实验页把两个结果并排留下给人看。

## CSS 端做了什么

`frontend/lqip.css` 先从 `rgb(from var(--lqip) ...)` 读取四个通道，再把量化字段还原成 Oklab。它没有先执行 `calc(var(--lqip) + pow(2, 31))`：Chromium 会在这个大数加法上发生浮点舍入，低位字段会悄悄改变。

底色在 Oklab 中插值：

```css
linear-gradient(180deg in oklab, var(--paper-base-start), var(--paper-base-end))
```

这不是装饰性选择。sRGB 直线会让某些蓝到红的路径穿过过宽的紫色区域，尤其会放大用户在双色样本里看到的酒红色。光斑依旧用 Paper 原来的 `hard-light`，所以它可以把渐变底色调亮，也可以调暗，而不是只盖一层白光。

## 跨语言互锁

Go、Rust、Zig 和 TypeScript 都实现了同一套过程算法：输入非预乘 RGBA，输出 `{ lqip: "#RRGGBBAA", lqipm }`。每个实现都公开 pack/decode API，测试中锁定同一批过程化 fixture：纯色、上下双色、左右双色、角落高亮、低对比和暖冷色块。

例如上下双色的 `skyOverGround` fixture 会选中 Paper single 的 mode 1：

```text
--lqip:  #5965f81e
--lqipm: 1
```

它不是手工挑出来的 CSS 样例，而是四门语言通过同一搜索和量化流程得到的字节。它也说明 mode 1 不是 Dual-A9，而是旋转后的单色 Paper。改动位布局时，golden、CSS 和四门实现必须一起变。

## 浏览器证据和人类判断

研究页把每张参考图同时做 native 和居中反向裁切，分成横向、纵向两组。当前页面有 34 张样本，三个页面分别展示单色方向、Dual-A9 方向以及两组胜者。每个样本只画一个绿色自动 winner；绿色框是指标提示，不是把人的视觉判断自动化。

另有一个不面向人类的 Chrome fixture：它把 34 × 4 个候选逐个截图，与数学渲染器的 PNG 做像素比较。最近一次验证覆盖 136 个 CSS cell，平均像素 RMSE 为 `0.00509`，最大为 `0.00652`。这组数字只证明 CSS 和数学模型互锁，不能证明某个样本“看起来最好”。

## 没有被协议解决的部分

固定六层 Paper 光场加一条 Dual-A9 轴，仍然无法表达所有局部多色分布。比如局部黄灯、肤色和黑色同时占据很短的空间距离时，两个 endpoint 可能只能在颜色和光感之间做取舍。这不是继续扭曲评分函数就能消失的误差。

Axis-16、二维 Mesh 和五基色实验都说明了额外容量可以换来表达能力，但它们也引入了新的 CSS 分支、不同的光感或尚未通过用户视觉验收的假设。因此它们现在留在研究档案里，没有进入四 mode 公共协议。

我愿意把当前结果称为一个收敛点，而不是终点：PaperCSS 的光感被保留下来，颜色从单一色相扩展到两个 Oklab endpoint，方向作为 mode 的最低位独立存在，四门实现和真实浏览器渲染可以互相验证。剩下的问题应该由新的视觉证据推动，而不是由更复杂的评分函数掩盖。
